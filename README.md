# ZK Credit Score

A minimal protocol proving credit-score eligibility with a Zero-Knowledge Proof,
without ever revealing the exact score.

[![CI](https://github.com/4alls/ZK-Credit-Score/actions/workflows/ci.yml/badge.svg)](https://github.com/4alls/ZK-Credit-Score/actions/workflows/ci.yml)

> Status: work in progress / portfolio project. Not audited, not production-ready.

## The problem

A lender wants to know: *"is this user's credit score at least 700?"*

The naive way requires revealing the exact score (742, say) to the lender.
That leaks more information than necessary — the lender only needs a yes/no
answer to the threshold question, not the precise number.

## The idea

The user proves, with a cryptographic Zero-Knowledge Proof:

> "I know a credit score that is within a realistic range, and that score is
> greater than or equal to the public threshold you asked about."

The proof reveals nothing else. The private score (`742`) never appears
anywhere — not in the proof, not on-chain, not in any log.

```
private input:  creditScore = 742      (never revealed)
public input:   minimumScore = 700     (the question being asked)
public input:   userAddress            (binds the proof to one Ethereum
                                         address, see "Security notes")
public output:  isEligible = 1         (the answer, and nothing more)
```

## How it works

```
User (knows creditScore privately)
        │
        ▼
  Circom circuit ──── enforces creditScore in [300, 850]
        │             and creditScore >= minimumScore
        ▼
  Groth16 proof  ──── a few hundred bytes, cheap to verify on-chain
        │
        ▼
  Solidity verifier ── pure cryptographic proof check
        │
        ▼
  ZKCreditRegistry ─── proof-specific safety: no replay, proof bound
                        to msg.sender, threshold cannot be forged
```

## Scope of this project

This is intentionally a **small, focused** project — it demonstrates the
core ZK proof pipeline end to end, not a full lending protocol. Specifically
in scope:

- a Circom circuit proving `creditScore >= minimumScore` (see
  [`circuits/`](circuits/))
- the full Groth16 workflow: compile, trusted setup, prove, verify
- a Solidity verifier + registry with real security analysis (replay
  protection, proof-to-address binding, access control) — see
  [`contracts/`](contracts/) and its Foundry test suite

Out of scope, on purpose (documented here rather than half-built):

- a real credit score issuer with signed credentials — this version lets a
  user self-declare their score, so it demonstrates the ZK mechanics, not a
  production trust model
- a lending protocol built on top of eligibility
- a backend/API server

## Getting started

```bash
# circuits
npm --prefix circuits install
npm run circuit:test      # witness-level tests (Phase 1)
npm run circuit:compile   # .circom -> R1CS + WASM witness generator
npm run circuit:setup     # Groth16 trusted setup -> proving/verification keys
npm run circuit:prove     # generate a proof for circuits/inputs/example.json
npm run circuit:verify    # verify that proof locally, off-chain

# contracts
forge install foundry-rs/forge-std --no-git   # first time only
forge build
forge test
```

Requires [`circom`](https://docs.circom.io/getting-started/installation/)
(the compiler) and [Foundry](https://book.getfoundry.sh/getting-started/installation)
installed and available on your `PATH`.

## The Groth16 pipeline, and what each file is

Groth16 needs a one-time, circuit-specific **trusted setup** before any proof
can be produced. `npm run circuit:setup` runs it in two stages:

1. **Powers of Tau** (generic, works for any circuit up to a size limit) — a
   ceremony where participants each contribute randomness ("toxic waste")
   that they must then destroy. The result is safe as long as *at least one*
   contributor was honest ("1-of-N" trust).
2. **Circuit-specific setup** — encodes this exact circuit's R1CS into a
   **proving key** (`.zkey`), from which a **verification key**
   (`verification_key.json`) is derived.

> **This repo's setup is a single-contributor toy ceremony**, generated
> locally by the scripts — convenient for a demo, but **not** a secure
> trusted setup. A production system needs a public multi-party ceremony
> (e.g. the Hermez/Polygon Powers of Tau ceremony) so the "1-of-N honesty"
> assumption is actually meaningful.

| File | What it is | Committed to git? |
|---|---|---|
| `.r1cs` | The circuit's constraint system | No — regenerated by `circuit:compile` |
| `.wasm` | Computes the witness from inputs | No — regenerated by `circuit:compile` |
| `witness.wtns` | One concrete solution (incl. the private score) | No — local only, never share this file |
| `.ptau` | Generic Powers of Tau parameters | No — large, regenerated by `circuit:setup` |
| `_final.zkey` (proving key) | Used by the prover to build a proof | No — regenerated by `circuit:setup` |
| `verification_key.json` | Used by anyone to verify a proof | **Yes** — small, public by design |
| `proof.json` / `public.json` | One generated proof + its public signals | No — example output, regenerated by `circuit:prove` |
| `contracts/src/verifiers/CreditScoreVerifier.sol` | The verification key, compiled to Solidity | **Yes** — needed to deploy the on-chain verifier |

The rule of thumb: **anything regenerable from the circuit source is
gitignored**; only the small, public artifacts needed to *use* the system
without redoing the setup are committed.

## Contracts

`ZKCreditRegistry.sol` sits on top of the generated `CreditScoreVerifier.sol`
(a pure, stateless Groth16 pairing check) and adds the on-chain state and
safety checks a real integration needs:

- `proveEligibility(pA, pB, pC, pubSignals)` — verifies the proof, then
  records `provenThreshold[msg.sender] = pubSignals[1]` (the threshold that
  was actually proven, read from the verified signal itself).
- `isEligible(user, threshold)` — a view function a downstream contract
  (e.g. a lending protocol) would call to gate on eligibility.

## CI

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every push to
`main` and every pull request, as two independent jobs:

- **`circuits`** — installs `circom`, then runs the full pipeline from
  scratch: compile, witness-level tests, trusted setup, prove, verify. This
  catches circuit regressions that unit tests alone might miss (e.g. a
  change that compiles and passes witness tests but breaks the exported
  Solidity verifier's public-signal layout).
- **`contracts`** — `forge fmt --check`, `forge build`, `forge test`.

The two jobs don't depend on each other: `contracts` tests against the
*committed* `CreditScoreVerifier.sol` and a proof fixture baked into the test
file (see `contracts/test/ZKCreditRegistry.t.sol`), not against whatever the
`circuits` job just regenerated — the trusted setup produces different key
material on every run (see "Security notes" below), so there is nothing
byte-for-byte stable to compare across jobs anyway. This keeps `forge test`
fast and dependency-free, and matches how a contributor who only touches
`contracts/` would actually work.

## Security notes

- **Range constraint**: the circuit forces `creditScore` into a realistic
  `[300, 850]` range using bit-decomposition (`Num2Bits`) before any
  comparison, to prevent field-overflow tricks against circomlib's
  comparators.
- **Trusted setup**: Groth16 requires a circuit-specific trusted setup. This
  is a real trust assumption of the system — documented, not hidden.
- **Self-declared score**: in this reduced scope, the user supplies their own
  `creditScore` with no issuer signature. The system proves the *threshold
  logic* correctly, but does **not** prove the score is truthful. A
  production system would require a signed credential from a trusted score
  provider (see "Out of scope" above).
- **Proof-to-address binding (front-running / proof theft)**: a Groth16 proof
  is, by itself, just a public statement — anyone who observes a valid
  `(proof, publicSignals)` pair (e.g. in the mempool before it confirms) could
  resubmit it from their own address and be marked eligible instead of the
  real prover. This is prevented by making the Ethereum address a **public
  signal of the circuit itself** (`userAddress`): the registry requires
  `pubSignals[2] == msg.sender`, and because that signal is part of what
  Groth16 cryptographically commits to, tampering with it invalidates the
  proof rather than just failing a Solidity-level check. Tested in
  `test_CopiedProof_RevertsWhenSubmittedByAnotherAddress` and
  `test_TamperedUserAddressSignal_RevertsAsInvalidProof`.
- **Replay protection**: each distinct proof (hashed as `keccak256(pA, pB,
  pC)`) can be consumed once, tracked in `usedProofs`. Tested in
  `test_SameProof_CannotBeSubmittedTwice`.
- **Threshold integrity**: `minimumScore` is read only from the verified
  `pubSignals[1]`, never from a separate function argument — there is no code
  path where a caller could claim a threshold higher than what their proof
  actually established. Tested in
  `test_TamperedMinimumScoreSignal_RevertsAsInvalidProof`.
- **No admin backdoor**: `verifier` is `immutable`. There is no owner, no
  upgradability, and no function that can redirect verification to a
  different (potentially malicious) verifier contract after deployment.
- **Trusting the verifier's math, not just its interface**: the registry
  does not attempt to re-implement or sanity-check the pairing check itself
  — that logic is exactly what Groth16's soundness guarantees are for. What
  the registry *is* responsible for, and what its tests target, is
  everything Groth16 soundness does **not** automatically give you: binding
  a proof to a specific caller, preventing reuse, and not trusting unverified
  parameters.
